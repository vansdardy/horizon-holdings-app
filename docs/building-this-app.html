A build, documented

Building Horizon Holdings

A portfolio tracker that fetches prices from the internet once a day, keeps a decades-long record in a single file, and installs like any other desktop program. This is how it was put together, and why each piece is shaped the way it is.

Python backend SQLite storage HTML interface Electron shell ~3,200 lines total v1.4.0 shipped

Most programming courses leave you at a fork. You have written programs that print to a terminal, and you have maybe written a web page. What nobody quite explains is how those become an application — the kind with an icon, that a person installs and opens without knowing what a terminal is.

This document walks through one real answer. The application is a portfolio tracker: it downloads closing prices for 78 companies across nine countries, converts between seven currencies, computes the daily value of a model portfolio, and compares it against what its owner actually holds. It runs on one person's laptop and is designed to keep an accurate record for twenty years.

You do not need to care about finance to follow it. The finance is just a source of genuinely hard requirements — real money, real precision, data that arrives late or not at all — and hard requirements are what force interesting design. Every decision here would look the same for a fitness tracker or a research logbook with equally unforgiving data.

What you should already know

Enough programming to read a function and know what a variable is. Some exposure to Python helps but is not required — the code samples are explained. No prior knowledge of databases, web servers, HTTP, or Electron is assumed; each is introduced where it first matters.

Part 01

What a desktop app really is

The surprising answer: mostly a web application with a babysitter.

Start with the word stack. Any application that stores information does three separable jobs, and they stack on top of each other:

  • Storage — where the facts live when the program is not running.
  • Logic — the rules that turn stored facts into answers.
  • Interface — what a human looks at and clicks.

"Full-stack" just means you are building all three rather than one. The stacking matters because the dependencies run one way: the interface asks the logic for answers, the logic reads and writes storage, and storage knows nothing about either. You can replace the interface entirely and the other two never notice. That property is what makes the desktop version of this app possible at all.

Here is the thing that takes a while to see. A desktop application does not need a fundamentally different architecture from a web application. It needs the same three layers plus a fourth job: something has to start the other pieces, put a window on screen, and clean up afterwards. That fourth job is what Electron does, and it is the entire difference.

Look at what that diagram implies. The window speaks to the backend over HTTP on 127.0.0.1 — an address that means "this same machine, don't go near the network". So the backend is a real web server that only ever serves one visitor. That sounds wasteful and isn't: it buys you a clean, inspectable boundary between interface and logic, it means you can debug the whole application with a browser and curl, and it means porting to a phone or a real website later is a matter of pointing something else at the same endpoints.

The alternatives, and why not

ApproachWhat it meansWhy not here
Native toolkit Write the interface in a desktop UI library (Qt, WinUI, Cocoa). Best performance and smallest download, but you write the interface again for each OS, and rich charts and tables are far more work than in HTML.
Just a website Host it, open it in a browser. Needs a server you rent and trust with financial data. The whole point here was that the data never leaves the laptop.
Rewrite in one language Port the Python to JavaScript so Electron runs everything. Tempting and tidy. But the market-data library doing the hard, undocumented work has no equally-maintained equivalent — see Part 05.
Shell + existing backend Keep the working code, wrap it in a window. Chosen. Largest download, but nothing that already worked had to be rewritten and re-verified.

Part 02

Decisions before code

Three choices made early that everything afterwards depended on.

Where does the truth live?

Before writing a line, answer this: if the program is deleted and reinstalled, what must survive? Here it is the price history, the NAV series, and the owner's positions. That answer names your storage layer, and naming it early stops you from accidentally keeping important state in three places.

The choice was SQLite: a complete relational database that lives in a single ordinary file, with no server to install or run. For a single-user application this is close to unbeatable. Backing up is copying a file. Inspecting it is one command. And unlike inventing your own format, you get transactions — an all-or-nothing guarantee that a half-finished write never leaves the file in a broken state.

In plain terms — transaction

A group of changes that either all happen or none do. If the power fails midway through writing 78 prices, you get the 78 from before, never 41 new ones and 37 old ones. Databases give you this; a text file you write yourself does not.

Put the logic where the libraries are

The application's hardest external job is getting prices out of Yahoo Finance, which has no official public interface. The community library that does it — yfinance — handles authentication cookies, retries, and impersonating a real browser's network fingerprint so requests are not blocked. That library is Python. So the backend is Python. This is a more useful rule than "pick the language you like": the language with the best library for your hardest problem usually wins the argument.

Build the fake data source first

This is the single highest-leverage decision in the project, and the one most often skipped. Before any code talked to Yahoo, there was a second implementation producing fake but deterministic prices from a hash of the ticker symbol. Same shape of data, same function signature, no network. 

def fetch(day_offset=0, window=1):
    if USE_MOCK:
        return fetch_mock(day_offset, window)   # deterministic fake prices
    return fetch_live()                          # the real Yahoo call

One environment variable switches them. The payoff is enormous:

  • Tests run in milliseconds and give identical results every time.
  • You can develop on a plane.
  • You are not hammering someone else's free service while debugging a loop.
  • Because the fake source accepts a day_offset, you can simulate a week passing in one second — which is the only sane way to test code that is supposed to do something once a year.
Why this matters more than it looks

The model portfolio rebalances on the first trading day of each calendar year. Without a fake clock, verifying that code means waiting until January. With one, it takes a second. Any behavior tied to real time needs a way to lie about time.

Part 03

The backend

Five files, each with one job, arranged so that dependencies point one way.

FileResponsibilityKnows about
config.pyRead settings, validate them, fail loudlynothing

db.pyEvery SQL statement in the projectconfig
marketdata.pyTalking to the outside worldconfig, universe
index_engine.pyThe portfolio mathematicsdb, universe
server.pyHTTP endpoints, the daily timerall of the above

Notice that the arrows never point backwards: db.py has no idea the portfolio math exists, and the math has no idea an HTTP server exists. You could delete server.py and still compute a NAV from a Python prompt. That is the test of whether your layers are real.

3.1 · Storage: let the schema enforce the rules

The interesting choice in the schema is not which columns exist but what the primary keys are. A primary key is a promise that no two rows can share it. Look at the prices table: 

CREATE TABLE IF NOT EXISTS prices (
    date   TEXT NOT NULL,
    ticker TEXT NOT NULL,
    close  REAL NOT NULL,
    PRIMARY KEY (date, ticker)
);

The key is the pair. This makes "one closing price per company per day" a fact the database physically cannot violate, rather than a rule your code has to remember. Combined with SQLite's ON CONFLICT ... DO UPDATE, re-fetching the same day is harmless: it overwrites rather than duplicating. Operations you can safely repeat are called idempotent, and building them that way removes an entire category of bug — the app can crash mid-fetch, restart, and simply run it again.

Storing dates honestly

Here is a bug that is easy to write and hard to notice. You fetch prices at 18:00 and stamp them all with today's date. But Tokyo closed hours ago, and the London exchange was shut for a holiday. If you stamp London's stale Tuesday price as Wednesday's close, you have invented a price that never existed — and next year, looking at a chart, you will have no way to know.

So every quote is stored under the session it actually traded in, taken from the data source itself. A market that was closed simply produces no row that day. Valuation then asks a different question — "what is the most recent close on or before this date?" — which is a small amount of extra SQL and the difference between a record you can trust in a decade and one you can't.

3.2 · Logic: the part that must be right

The model portfolio starts with a notional 10 billion Swiss francs, divided into 200 million shares, so one share is worth exactly 50.00 at inception. Each day it recomputes what those holdings are worth. Three details make it real rather than a toy:

  • Whole shares only. You cannot buy 3.7 shares of Nestlé. The allocation floors to an integer and keeps the remainder as cash, in that company's local currency.
  • Seven currencies. A Japanese stock is priced in yen, a Swiss one in francs. Everything converts through US dollars internally — because that is how the exchange-rate data arrives — then out to the reporting currency at the end.
  • Annual rebalance. On the first trading day of a new year, holdings are sold and rebought at target weights. 
def _allocate(nav_usd, prices, fx):
    """Buy integer shares at target weights; residual -> local-currency cash."""
    weights = u.target_weights()
    live = {t: w for t, w in weights.items() if prices.get(t)}
    wsum = sum(live.values())

    holdings, cash = {}, {}
    for t, w in live.items():
        ccy = u.UNIVERSE[t]["ccy"]
        alloc_usd   = nav_usd * (w / wsum)          # this stock's slice
        alloc_local = from_usd(alloc_usd, ccy, fx)  # into its own currency
        n = int(math.floor(alloc_local / prices[t]))  # whole shares only
        holdings[t] = n
        cash[ccy] = cash.get(ccy, 0.0) + (alloc_local - n * prices[t])
    return holdings, cash

Read the wsum line closely. If a company's price is missing, it is dropped from live and the remaining weights are renormalised so they still add to 100%. Without that, a missing price would silently leave part of the portfolio in cash and depress the return.

The bug this exists to prevent

An earlier version valued a missing price as zero. One company failing to fetch produced a 2.17% single-day loss that never happened. On a chart three years later that dip is indistinguishable from a real market event.

The fix is a refusal. If any held position has no price, the day's NAV is not written at all, and the API returns an error naming the companies. A gap in the record is honest and repairable; a wrong number is neither.

3.3 · The daily pipeline

One function ties it together, and the order of its steps is the design.

The loop over "each day with no NAV yet" is doing something else useful. Each fetch returns roughly ten trading days, not one. If the laptop was asleep for three days, those days have no NAV rows, so they get computed in order using the prices that were correct at the time. The application heals its own gaps without anyone noticing there were any.

3.4 · The API: naming what the interface can ask

An API endpoint is a URL that returns data instead of a page. The framework here is FastAPI, and defining one is almost anticlimactic: 

@app.get("/api/nav")
def api_nav():
    return {
        "history": db.nav_history(),
        "stats":   index_engine.stats(),
    }

The decorator says "when a browser asks for /api/nav, run this". The dictionary is converted to JSON automatically. The design work is not the syntax — it is deciding what questions the interface is allowed to ask. Getting that list right is most of what makes a frontend simple later.

One endpoint deserves special mention because it saved real time: /api/check_symbols tests all 78 ticker symbols against the data source and reports which ones resolve. Stock exchanges rename things — Roche's symbol changed during this project's life — and without this endpoint you discover it as a mysterious failure months later.

3.5 · Configuration, and failing loudly

Settings resolve in three layers: a real environment variable wins, then a .env file, then a built-in default. The .env file exists because environment variables set in a terminal die with that terminal, and this program is meant to run every day for years.

The part worth copying is what happens when a setting is wrong: 

if lo is not None and not (lo <= v <= hi):
    raise SystemExit(
        f"[config] {name}={v} is out of range; expected {lo}-{hi}.\n"
        f"          Fix it in {ENV_FILE}.")

It refuses to start, names the setting, states the valid range, and points at the file to edit. Compare that with the alternative: starting up happily and failing at 18:00 that evening with a confusing error. Validate configuration at startup, not at first use.

Part 04

The frontend

One HTML file, no build step, no framework — and the specific reasons that is defensible here.

The entire interface is a single file: markup, styling, and logic in one document you can open by double-clicking. There is no compilation, no node_modules, no bundler. For a modern web project this is unusual enough to need justifying.

It is defensible because of three properties of this application: one person uses it, the screen count is small and fixed, and it must still open in ten years. A build toolchain is the part of a project most likely to stop working — dependencies get abandoned, versions conflict, the build breaks on a new laptop. A file that needs nothing but a browser has no such failure mode.

When this stops being right

If several people edit the interface, or it grows past a few thousand lines, or you need components reused across pages, the single file becomes the problem instead of the solution. Reach for a framework then — but reach for it because you hit that wall, not by default.

The three things the page does

Strip away the styling and every screen follows the same shape: fetch, transform, render. 

async function loadNav(){
  const d = await api('/api/nav');   // 1. fetch — ask the backend
  NAV = d.history;                   // 2. transform — keep what we need
  renderNav();                       // 3. render — write it into the page
}

That is the whole architecture of the frontend, repeated for positions, prices, and fundamentals. No state-management library, because there are only a handful of variables and one place that changes each.

The one-line trick that makes both modes work

const API = (window.location.protocol === 'file:')
  ? 'http://127.0.0.1:8000'   // opened by double-clicking the file
  : '';                        // served by the backend, same origin

When the backend serves the page, requests go to the same address it came from, so the base URL is empty. When you open the file directly from disk, there is no server to be relative to, so it needs the full address. One line, and the page works in both situations — including inside Electron, which uses the first form.

Making the interface survive its own failures

The charting library was originally loaded from a CDN. If that failed — offline, blocked, a corporate proxy — then Chart would be undefined, and the first chart call would throw. Because the page is one long script, that single error stopped everything after it: the holdings table, the filters, the position editor. None of them needed charts. 

if (typeof Chart === 'undefined') {
  window.Chart = function(){ return { destroy(){}, update(){} }; };
  window.Chart.defaults = { font: {}, color: '', borderColor: '' };
  window.__CHART_MISSING__ = true;
}

A stub object that does nothing successfully. Every chart call becomes a harmless no-op, a banner explains that charts are unavailable, and the other 90% of the application keeps working. Degrade in proportion to what actually broke.

For the desktop version the library and fonts were downloaded into the project so there is no CDN to fail — a desktop app that needs the internet to draw a chart is not really a desktop app. The stub stayed anyway, now guarding against a damaged installation.

An honest wart

The list of 78 companies exists twice: once in universe.py and again as a JavaScript array inside the HTML. Changing the portfolio means editing both, and forgetting means the page and the API disagree.

This is a real design flaw, kept here deliberately as an illustration. The clean fix is to serve that data from an endpoint and delete the copy. It has not been done because the list changes roughly never, and the duplicate also holds fallback estimates the API does not have. That is a legitimate trade — as long as it is a decision and not an accident. The difference between technical debt and a mistake is whether it is written down.

Part 05

The desktop shell

Wrapping a working web application in a window turns out to be five specific problems, each with an obvious wrong answer.

Electron is Chromium plus Node.js in one package. It runs two kinds of process. The main process is Node: it has no user interface, but it can touch the filesystem, start other programs, and create windows. Each renderer process is a Chromium tab displaying a page. Your application code lives in main; your interface lives in a renderer.

For this project the main process has exactly one job: supervise the Python backend. Start it, wait for it, point a window at it, and make sure it dies when the app does. That is where the five problems live.

Problem 1 · Which port?

The obvious answer is to hardcode 8000. It fails the first time something else is using 8000 — including a copy of this same backend the user started from a terminal. Instead, ask the operating system for any free port: 

function freePort() {
  return new Promise((resolve, reject) => {
    const srv = net.createServer();
    srv.listen(0, '127.0.0.1', () => {        // 0 means "you pick"
      const { port } = srv.address();
      srv.close(() => resolve(port));         // release it, hand the number over
    });
  });
}

The port number is then passed to Python as an environment variable, and the window is pointed at whatever it turned out to be.

Problem 2 · When is it ready?

Starting a program and immediately loading a page from it does not work — Python takes a moment to boot. The tempting fix is to wait two seconds. That is wrong in both directions: too slow on a fast machine, and still too short on a cold first launch, producing a bug that appears only on other people's computers.

Ask instead of assume. Poll the status endpoint until it answers: 

const req = http.get({ host:'127.0.0.1', port, path:'/api/status' }, res => {
  if (res.statusCode === 200) resolve();      // it's alive
  else retry();
});
req.on('error', retry);                        // not listening yet — try again
// retry() waits 300ms, gives up after 90 seconds

This is ready as soon as the backend is, waits as long as genuinely needed, and — because there is a deadline — reports a real error instead of hanging forever.

Problem 3 · How does it die?

This one is genuinely surprising. On Windows, killing a process does not kill the processes it started. Quit the app carelessly and Python keeps running — holding the port and the database file — until the user finds it in Task Manager. Worse, the next launch appears to work while writing to a database another invisible process also has open. 

// child.kill() signals only the direct child.
// /T takes the whole tree, which matters because the frozen bundle's
// launcher and the Python process it starts are two different PIDs.
execFile('taskkill', ['/PID', String(pid), '/T', '/F'], () => {});

Problem 4 · What if it is opened twice?

Double-clicking the icon again would start a second backend, with a second daily timer, both writing to one database. Electron has a built-in answer: 

if (!app.requestSingleInstanceLock()) {
  app.quit();                       // another copy already owns the lock
} else {
  app.on('second-instance', showWindow);   // raise the existing window instead
}

Problem 5 · Where do files go?

During development the database sat next to the source code, which is convenient and completely wrong for an installed program. Installation directories are read-only for good reason, and an update replaces that folder wholesale — taking the user's data with it.

Installed applications write to a per-user data directory that the OS names for you (app.getPath('userData')). The backend already accepted a database path as an environment variable, so the shell simply passes the right one, and Python needed only a small change to know it was frozen: 

FROZEN = getattr(sys, "frozen", False)   # PyInstaller sets this

def _default_data_dir():
    if not FROZEN:
        return HERE                      # running from source: unchanged
    base = os.environ.get("APPDATA") or os.path.expanduser("~")
    return os.path.join(base, "HorizonHoldings")

Note the shape of that function: the new behavior applies only when frozen, so the old workflow is bit-for-bit unaffected. When adding a mode, make the existing mode the untouched path.

Problem 6 · When the page needs to do something a page cannot do

The five problems above are all about supervision. This one is about the boundary itself, and it arrived the way real requirements usually do — from someone using the thing.

Importing a database was originally only available from the tray menu. That is a defensible place for it, and it was still wrong, because the person who asked for the feature later went looking for it in the window, did not find it, and concluded it had never been built. A feature nobody can find has the same value as a feature that does not exist.

So it needed a button in the page. Which runs straight into the architecture: the page is a Chromium tab. It cannot open a native file dialog, cannot stop and restart a process, and cannot read arbitrary paths. Not because Electron forgot, but because a renderer having those powers is precisely what makes a compromised page catastrophic instead of annoying.

The sanctioned route is a preload script: a small file that runs in the renderer with access to Electron's APIs, before the page loads, and hands the page an explicitly chosen set of functions. 

// preload.js — runs in the renderer, but privileged
const { contextBridge, ipcRenderer } = require('electron');

contextBridge.exposeInMainWorld('desktop', {
  importDatabase: () => ipcRenderer.invoke('db:import'),
  version:        () => ipcRenderer.invoke('app:version'),
});
// main.js — the privileged side actually doing the work
ipcMain.handle('db:import',   () => importDatabaseNow(userData));
ipcMain.handle('app:version', () => app.getVersion());
// the page — no Node, no filesystem, just the two functions
if (window.desktop) {
  importBtn.style.display = '';
  importBtn.onclick = () => window.desktop.importDatabase();
}

Three details in there matter more than they look:

  • Expose named functions, never ipcRenderer itself. Handing the page the raw channel object lets it invoke every handler the main process has. This is the single most common way the pattern is undone, and it undoes it completely.
  • The privileged action still confirms with the user. The import shows a file picker and a warning dialog. Even a fully compromised page achieves nothing worse than a dialog somebody has to agree to.
  • window.desktop is also feature detection. In an ordinary browser it is undefined, so the button stays hidden rather than appearing and failing. The same file is served both ways, and each gets a coherent interface.
The trap this immediately walked into

electron-builder only packages the files listed in package.json's files array. Adding preload.js to the project does not add it to the build.

In development the preload loads from disk and everything works. In the installed app the file is absent, window.desktop is undefined, and the button silently never appears — the feature is gone, with no error anywhere. Another entry in the "works in dev, broken when packaged" family from Part 08, found the same way: by checking the list rather than trusting it.

Turning Python into an executable

The user's computer has no Python installed, so it must travel with the app. PyInstaller bundles the interpreter, every library, and the program into a folder with an .exe in it. Two decisions matter:

  • One folder, not one file. PyInstaller can produce a single executable, but it works by unpacking ~90MB into a temporary directory on every launch. The folder version starts immediately.
  • Hidden imports. PyInstaller finds libraries by reading your import statements. Libraries loaded dynamically by name are invisible to it and simply go missing. Both offenders here needed declaring: uvicorn picks its networking code by string at runtime, and curl_cffi ships a compiled library and a certificate bundle that are data files, not imports. 
for pkg in ("yfinance", "curl_cffi"):
    d, b, h = collect_all(pkg)          # grab data files and binaries too
    datas += d; binaries += b; hiddenimports += h

hiddenimports += collect_submodules("uvicorn")
Verify the bundle before wrapping it

The frozen backend was run on its own and pointed at the real Yahoo service before Electron was involved at all: 78 of 78 symbols resolved and a full fetch wrote 789 rows. Had that failed, the cause would have been obvious. Discovering it through a blank Electron window would not have been.

Keeping the timer alive

The application promises to fetch prices at 18:00 daily. Closing a window normally ends a program — which would silently break that promise. So closing hides to the system tray instead, and only an explicit Quit exits: 

mainWindow.on('close', e => {
  if (!isQuitting) { e.preventDefault(); mainWindow.hide(); }
});
app.on('window-all-closed', () => {});   // deliberately does NOT quit

This is a real product decision, not a technical one, and it needed asking about rather than assuming. The alternative — quit fully, catch up on next launch — is perfectly valid, and works here precisely because the backfill logic from Part 03 already exists.

Part 06

Running on three systems

Electron and Python are both cross-platform. The gaps are narrow, specific, and worth knowing before you promise anyone a Mac version.

ConcernWindowsmacOSLinux
Kill the backend taskkill /T /F SIGTERM to the process group
Data directory %APPDATA% ~/Library/Application Support ~/.config
Closing last window App keeps running (tray / menu bar) Same, tray support varies by desktop
Installer format NSIS .exe .dmg AppImage / .deb
Freezing Python Must build on each OS — PyInstaller cannot cross-compile
Unsigned app SmartScreen warning Refuses to open without a paid certificate Generally fine

Two of those rows deserve emphasis. PyInstaller cannot cross-compile — a Mac build must be produced on a Mac, because it is embedding that platform's actual Python binary. This is the single biggest practical obstacle to shipping a multi-OS desktop app with a bundled runtime, and the usual solution is a continuous-integration service that builds on all three.

And macOS is materially stricter about signing. An unsigned Windows app shows a warning the user can click past; an unsigned Mac app is refused outright unless the user goes digging in settings. Signing requires a paid developer account. Budget for it before promising a Mac release.

The engineering response to all of this is the same one that made the desktop version cheap in the first place: isolate the platform-specific code in one place. In this project every OS difference lives in the shell, and the entire Python backend — which is most of the application — is unaware which operating system it is on.

Part 07

Build it yourself

The same project, in an order where every step ends somewhere you can stop.

The sequence matters more than the specific technologies. Each stage produces something you can run and check before the next one adds complexity. If you are following along with your own idea, substitute your domain wherever this one appears.

  1. Decide what must survive deletion

    Write down the tables before writing code. Pick primary keys that make your rules impossible to break. Create the database and write one row by hand.

    ✓ You can open the file and see your row.

  2. Write the fake data source

    Before touching a real service, write the function that returns plausible made-up data with the exact shape the real one will return. Put both behind one function and an environment variable. 

    def fetch():
    return fetch_mock() if USE_MOCK else fetch_live()

    ✓ You can generate a week of data instantly, offline.

  3. Write the logic, with no interface at all

    Pure functions: data in, answers out. Test them from a Python prompt. This is where correctness is won — it is much harder to reason about a calculation once a button is attached to it.

    ✓ You can compute a correct answer from a terminal.

  4. Put HTTP endpoints in front of it

    Install FastAPI and expose the questions the interface will ask. Visit /docs — FastAPI generates an interactive page listing every endpoint, which you can click to test. 

    pip install fastapi "uvicorn[standard]"
python server.py     # then open http://127.0.0.1:8000/docs

    ✓ You can get real JSON in a browser.

  5. Build the interface as a plain web page

    One HTML file. Fetch from your endpoints, put the results in the document. Do not think about the desktop yet — everything you build here carries over untouched.

    ✓ A working web app in your browser.

  6. Remove every outside dependency the page has

    Download any libraries and fonts loaded from a CDN into your own folder and repoint the tags. A desktop app must work with the network unplugged.

    ✓ Turn off wi-fi; the page still renders fully.

  7. Make the backend safe to install

    Accept the database path, settings path, and port as environment variables. Make sure nothing is written next to the program itself. 

    PORTFOLIO_DB=/tmp/test.db PORT=9001 python server.py

    ✓ Runs correctly with its data somewhere else entirely.

  8. Freeze the backend

    Bundle it with PyInstaller and — importantly — run the result on its own before adding Electron. Fix hidden-import problems here, where the error messages are still readable. 

    pip install pyinstaller
python -m PyInstaller backend.spec --noconfirm \
  --distpath build/backend --workpath build/pyinstaller

    ✓ The executable serves your API with Python uninstalled.

  9. Add the shell

    Now write the Electron main process, solving the five problems from Part 05 in order: free port, spawn, poll for readiness, window, teardown. 

    cd desktop && npm install && npm start

    ✓ Your app opens in its own window.

  10. Package it

    electron-builder produces the installer, bundling the frozen backend alongside. Then test it the way a stranger would: install on a machine that has never had your development tools. 

    npm run dist

    ✓ Someone else can install and open it.

The rule behind the ordering

Every step is runnable. You are never more than one step from something that works, so when something breaks you know exactly what caused it. The opposite approach — building all the pieces and connecting them at the end — produces a failure with ten possible causes and no way to isolate any.

Part 08

Shipping it

The distance between "it runs" and "a stranger can install it" is short, and it is where the last bugs are hiding.

Everything so far ran on the machine that built it, out of a folder full of source code, started from a terminal. Shipping means producing one file that someone else double-clicks. Three artifacts get made, each wrapping the previous one:

ArtifactMade byWhat it isSize
Frozen backend PyInstaller A folder with .exe + interpreter + every library 89 MB
Packaged app electron-builder Electron runtime, your JS, the frozen backend inside resources/ 358 MB
Installer electron-builder (NSIS) One .exe that unpacks the above and makes shortcuts 110 MB

Test the artifact you ship, not the one you develop

This is the whole lesson of this part, and it cost two real bugs to learn. Both were found by running the packaged build. Both were completely invisible when running npm start, and both were in the same feature — the one that brings an existing database across on first launch.

Bug 1 — a path that means something different once packaged

The migration looked for the database at REPO/portfolio.db, where REPO was path.join(__dirname, '..'). In development that is the project folder and it works. Once packaged, __dirname is inside the app archive, so REPO points at resources/ — a folder that has never contained a database. The check found nothing and returned silently.

The result was not an error message. The backend found no database, created an empty one, and because the launch happened after the daily fetch hour, the scheduler immediately downloaded prices and seeded a brand-new index. A second, discontinuous track record, looking entirely legitimate, while the real history sat in a file the app never looked at.

Bug 2 — the safe-looking default that wasn't

The fix for Bug 1 was to ask the user: Import an existing database, or start fresh? Two buttons, with "start fresh" as the cancel action. But a dialog's cancel action is also what you get for pressing Escape or clicking the X — so dismissing the question without reading it silently chose the destructive option.

The corrected version has three buttons and makes Quit the cancel action. Now the accidental path changes nothing, and creating a new series takes a deliberate click. Ask what your cancel action does, because that is what a distracted user picks.

Not every build failure is a bug in your code

The first attempt to build the installer died with Cannot create symbolic link. Nothing in this project creates symbolic links. The packager downloads a code-signing toolkit that contains macOS library symlinks, and creating symlinks on Windows needs a privilege ordinary accounts do not have — while the app was not being signed at all.

Learning to read that difference quickly matters. The error was in the environment, and the fix was to populate the tool's cache by hand, skipping the macOS files nothing needed. Time spent re-reading your own code would have been wasted.

Ship the explanation with the product

The document you are reading is bundled into the application. The backend serves it at /guide, and there is a tray entry and a header link that open it in its own window — so it works with the network unplugged, exactly like everything else here.

Documentation that lives somewhere else goes stale, because updating it is a separate act you can forget. Documentation that ships in the same artifact gets rebuilt every time the app does.

A release checklist

  1. Re-freeze the backend if any Python changed.
  2. Build the installer.
  3. Run the packaged app — not the dev one — from its output folder.
  4. Delete your own data directory first, so you see what a new user sees.
  5. Check the first-run path specifically; it is the one you never exercise.
  6. Confirm the app fully exits and leaves no process behind.

Step 4 is the one people skip. Your machine has state from a hundred test runs; a new user's has none, and almost every first-run bug hides in that gap.

Part 09

Knowing it works

Everything so far was verified by someone running it and looking. That stops scaling almost immediately.

The question that prompts this part is a good one: an AI assistant wrote most of this code — how does anyone know it does what it claims?

The useful move is to notice that the question is not really about AI. Code you wrote yourself six months ago has exactly the same problem: you cannot remember what it was supposed to do, and reading it tells you what it does now, which is the thing under suspicion. "Do I trust the author" is the wrong question, because the honest answer is always no. The question is how would I find out.

A test is a second, independent statement of what the code is for. Its value comes from being written separately: when the two disagree, one of them is wrong, and you find out in a second rather than in a year.

The one that matters most here

This project's central promise is that a NAV series is never silently wrong. So the most valuable test in the suite deliberately breaks that situation: seed the index, remove the price of a position that is actually held, and assert that the day is refused — no NAV row written, and the error naming the offending ticker.

That is a test of a behaviour someone might "fix" later without knowing why it exists. It now fails loudly if they do.

Three layers, and honest proportions

Testing the backend

The backend was easy to test, and not by luck — it was already arranged as pure functions over plain data. index_engine takes prices and rates and returns numbers. Nothing to mock, nothing to start. 

def test_allocation_buys_whole_shares_only(fx, prices):
    holdings, _ = eng._allocate(1_000_000.0, prices, fx)
    for ticker, n in holdings.items():
        assert isinstance(n, int), f"{ticker} got a fractional share count"

Two techniques carried most of the weight. First, fixtures that make the arithmetic checkable by hand: every currency is worth exactly one dollar and every stock costs exactly ten. Nothing realistic — which is the point, because a failing assertion then points at the logic rather than at a number nobody can verify by reading.

Second, substituting the database path per test. This works only because db.conn() reads the path when it is called rather than capturing it at import. That was not done for testability, but it is the difference between a suite that isolates cleanly and one that needs a running database.

One trap in the API tests

FastAPI's test client runs the application's startup sequence when used as a context manager — which here starts the daily scheduler. A test suite whose behaviour depends on what time of day it runs is worse than no suite, because it teaches people to ignore failures. The client is deliberately not used that way.

Testing the frontend, which is the part nobody explains

The phrase suggests robots clicking buttons, and that impression is most of why people never start. It is worth replacing with something more useful: look at the bugs frontends actually have. A currency converted the wrong way. A date window off by one. A missing value rendered as 0 instead of a dash. None of those are about clicking. They are ordinary function bugs that happen to live in a file the browser loads.

So there are three separable things, and they are usually conflated:

LayerWhat it checksToolsWorth it?
Pure logic Formatting, conversion, filtering, calculation Node's built-in runner; no dependencies Always. Cheap and catches most real bugs
DOM behaviour Clicking this renders that; the empty state appears jsdom, Testing Library Once the interface has real interaction
End to end The whole app, in a real browser, against a real backend Playwright, Cypress For flows where failure is expensive

This project has the first layer and not the other two, deliberately. Adding Playwright means several hundred megabytes of browser binaries and a suite that takes minutes, to test a single-user application whose main flows are exercised by its owner daily. That is a defensible answer — but only when it is a decision, not an omission, which is why it is written down here.

The obstacle, and what it was really telling us

The frontend functions could not be tested at first. Not because testing browsers is hard, but because of this: 

function inBase(usd){          // before
  if(BASE === 'USD') return usd;
  const r = FXRATES[BASE];     // BASE and FXRATES are page-level variables
  return r ? usd / r : null;
}

You cannot call that without recreating the whole page around it, because two of its three inputs are invisible. "This is hard to test" is almost never a fact about testing. It is a fact about the code — here, that the function had hidden dependencies.

The fix is not clever. Every input becomes a parameter:

function inBase(usd, base, fxRates){   // after — same body, visible inputs
  if(base === 'USD') return usd;
  const rate = fxRates ? fxRates[base] : null;
  return rate ? usd / rate : null;
}

Now it is testable, and independently better: a reader can see what it depends on from the signature. The page keeps a one-line adapter (const inBase = usd => LIB.inBase(usd, BASE, FXRATES)) so not a single call site changed. That last detail is what made the change safe enough to do at all — see the next part.

The extracted file uses a small wrapper so a <script> tag and Node's require both work, keeping the project's no-build-step bargain intact. Then the tests are unremarkable, which is the goal: 

test('a missing rate yields null, never zero', () => {
  // Zero is a number a reader would believe. Absence has to look like absence.
  assert.equal(lib.inBase(100, 'CHF', {}), null);
});

What to test, and what not to

Worth testingNot worth testing
Rules that would be expensive to get wrong That a framework does what its docs say
Anything with edge cases: null, zero, empty, boundaries Getters, setters, code with no decisions in it
Behaviour someone might "helpfully" undo later Exact wording and pixel positions, which change for cosmetic reasons
Every bug you fix — one test, so it stays fixed Anything you would delete rather than repair
A test that has never failed has proved nothing

A test can pass because the code is right, or because the test asserts nothing. The two look identical from the outside. Break the code on purpose once and watch it go red — that, not the green run, is the moment it starts being worth something.

Writing this suite produced a small example of the same principle in reverse: one test failed because 105/100 - 1 is 0.050000000000000044 in binary floating point. The code was correct; the test was wrong to compare computed floats exactly. That is a normal outcome and not a wasted hour. 

python -m pytest tests/ -q            # 52 backend tests, about 7 seconds
node --test tests/js/*.test.js       # 22 frontend tests, under a second

Part 10

Keeping it changeable

Code does not rot on its own. It rots because each change is made in a hurry, in the shape the last change left behind.

Refactoring means changing how code is arranged without changing what it does. The second half is the load-bearing part. Rewriting a function and also fixing a bug in it is not refactoring; it is two changes wearing one coat, and when something breaks you will not know which one did it.

Why it has to be continuous

This project has been shipping quickly, and the cost showed up exactly where you would expect. Importing a database ended up implemented twice: once for the first run, once for the tray menu added later. The second one validated that the chosen file was actually a SQLite database. The first one never did.

So at first run you could select a PDF, and the app would copy it over portfolio.db and then fail to start — with an error about the backend, several steps away from the actual mistake. Nobody decided that. It is what happens when the same job exists in two places and only one of them gets fixed.

The repair, and why it is small

One function, pickDatabaseFile(), that asks for a file and refuses anything without the SQLite header. Both paths call it. The duplicate check is gone and there is now one place where this rule lives, so the next fix cannot reach only half the application.

The prerequisite nobody can skip

Refactoring without tests is not refactoring. It is editing code and hoping, because the entire claim — "behaviour is unchanged" — is exactly the thing you have no way to check.

This is why the previous part comes first. Both of today's refactors were done in the same order: write tests describing current behaviour, change the structure, run the tests. When 74 of them still pass, "I did not break anything" is a statement with something behind it.

Four habits that make it cheap

  1. Move the body, keep the name. The frontend extraction touched zero call sites, because the page kept one-line adapters with the original names. A refactor that forces you to edit two hundred lines is a refactor you will not do; one that forces you to edit three is one you will do on a Tuesday.
  2. One kind of change per commit. Structure or behaviour, never both. Then a bisect points at something meaningful, and a review is readable.
  3. Rename first. Renaming is the safest refactor and often the most valuable — half of "this code is confusing" is things being called the wrong thing. It also makes the next step obvious.
  4. Small enough to abandon. If a refactor cannot be thrown away after twenty minutes without losing real work, it is too big. Split it.

When to do it, and when to leave it alone

Refactor whenLeave it when
You are about to add something and the shape fights you It is ugly but you have no concrete complaint
The same logic exists in three places (two is a coincidence) The code is about to be deleted anyway
You had to explain it out loud to understand it Nobody has touched it in a year and it works
A bug appeared because two copies disagreed You have no tests and no time to write any

The last row on the right is not an excuse to never refactor — it is a statement about ordering. Write the test first, then refactor. If neither is affordable today, leave the code alone and be honest that you are choosing to.

Principles, and why learning them first backfires

There is a canon here — single responsibility, interface segregation, Liskov substitution, dependency inversion, and a shelf of patterns with names like Observer and Factory. They are genuinely useful. They are also one of the most reliable ways to stop a person from writing any code at all, and that failure deserves a straight answer rather than a reading list.

Here is what those names actually are: compressed descriptions of pain that experienced people already felt. Someone changed a class for the fourth unrelated reason, got annoyed, and named the annoyance "single responsibility". The principle is the label on the scar, not the plan that prevented it.

Learning them as a checklist inverts the order, and the result is exactly the paralysis people describe. You sit down to write a feature and find yourself designing for problems you do not have, evaluating six patterns for a function that will be forty lines, trying to hold the entire system and every detail in your head simultaneously. That is not rigour. It is a thinking task that has been made artificially impossible.

The order that works

Write the simplest thing that works. Notice a specific pain. Then let the principle name the fix.

The pain always arrives as a concrete sentence, never as a principle: "I can't test this without starting a browser." "I changed the price format and the tray broke." "There are two of these and I fixed one." Each of those has a well-known answer, and you will find it far faster when you already know which problem you have.

Today's frontend extraction is a clean illustration. Its result satisfies single responsibility and dependency inversion — the logic no longer knows where its inputs come from. At no point did anyone think either phrase. The trigger was: I cannot test this function because two of its inputs are invisible. The principles describe the outcome accurately, and would have contributed nothing to reaching it.

A modest set is worth internalising early, because each is a sentence rather than a framework:

  • Make inputs visible. A function that reads hidden state is hard to test, reuse, and reason about.
  • One reason to change. If two unrelated requirements edit the same function, they will eventually collide.
  • Two is coincidence, three is a pattern. Do not abstract on the second occurrence; you cannot see the shape yet.
  • You are not going to need it. Speculative flexibility is the most expensive kind, because you pay for it before knowing if it was the right shape.

And one exception worth respecting: principles do pay upfront at boundaries you cannot change later. A database schema, a file format, a public API, anything already on other people's machines. Inside a function, refactor freely. At a boundary, think first — because there the cost of being wrong is not a refactor, it is a migration.

If you have previously given up because software felt like it required holding everything at once: it does not, and the people who look like they are doing that are not. They are writing something simple, noticing what hurts, and fixing that one thing — which is a much smaller task, and the only one anybody actually performs.

Part 11

Keeping track of changes

Two people need to know what changed — whoever uses your app, and you. They need completely different answers.

Before reading on, try to answer four questions about the project as it now stands. They are not rhetorical; attempt them.

  1. The scrollbar behaves differently than it did earlier. What exactly changed, and in which file?
  2. The first-run import worked, then broke, then was fixed twice. What did the version that worked look like?
  3. You want to undo the tray menu changes but keep the scrollbar work. How?
  4. A stale -wal file gets deleted before a database is copied. Six months from now, why?

If your honest answer to any of them is "I would have to remember", or "I'd look for a folder called main_old.js", then you have just found the problem this part is about — and you found it the way almost everyone does, which is slightly too late to be comfortable.

Everything described in this document up to here was built with no record of its own construction. Each edit overwrote the one before it. The application works, and the sequence that produced it is simply gone. There is no way to see the state before any given change, and no way back to it.

What that costs, concretely

Both bugs in Part 08 were introduced by edits made while fixing something else. Finding them meant re-reading the current code and reasoning forwards. With a record of changes, "what did I touch between the version that worked and this one?" is one command, and the answer is usually sitting in the output.

A third bug in this project was a CSS comment accidentally left unclosed, which the browser's error recovery hid. A diff would have shown it as five stray lines the instant it was made.

So there are two tracking problems here, and confusing them is common:

For whoever uses itFor you
The question "Should I install this one?" "What changed, and how do I get back?"
The answer A version number Version control — in practice, git
How often A few releases a year Every change worth naming
They see 1.1.0 → 1.2.0 Every intermediate state, forever

For whoever uses it: what the three numbers mean

The widely used convention is semantic versioning: MAJOR.MINOR.PATCH.

BumpWhenThe user reads it asExample here
MAJOR
1.0.0 → 2.0.0		 Something that used to work no longer does, or works differently "Set aside time; read the notes" Changing the reporting currency, which invalidates an existing NAV series
MINOR
1.0.0 → 1.1.0		 New capability, everything old still behaves the same "Safe; there is new stuff" 1.2.0: importing a database at any time, without losing what is there
PATCH

Two consecutive releases here were both minor bumps, for the same reason. 1.1.0 added an embedded guide, two named tray commands in place of one ambiguous one, and an overlay scrollbar. 1.2.0 added the ability to import a database at any time. Both added capability; neither changed how anything existing behaves, and existing databases keep working untouched. The number lives in package.json, which is where the packager reads it and where the app reports it in its own tray menu.

Show the version somewhere

If a user cannot tell you what version they are running, you cannot help them. It costs one line in a menu, and it is the first question you will ask about every bug report you ever receive.

The loop, and the step everyone forgets

That trap is worth dwelling on because the symptom is so misleading. You change a line of Python, restart the app, and the behavior does not change. The file is right there with your edit in it. Nothing is broken, nothing logs an error — the shell is simply running a bundle that was built before you made the change.

Anywhere you have a build step, you have this class of bug. The habit that prevents it is to make "rebuild the thing that gets consumed" part of running the app, rather than a step you remember.

For yourself: version control

Git is the near-universal answer, and the mental model is simpler than its reputation. Git stores snapshots of your whole project. You decide when one is taken, and you attach a message saying why. Afterwards you can read any snapshot, compare two of them, or return to one exactly.

Three commands do almost all of the work:

git init                      # start recording — once, per project
git add -A                    # stage everything that changed
git commit -m "why this change exists"

And two that pay it back:

git log --oneline             # the sequence of snapshots
git diff                      # exactly what changed, line by line

The message is the part beginners skip and experienced people guard. The diff already shows what changed; only the message can say what it was for. "Fixed stuff" throws that away. Compare it with the actual message attached to the import feature in this project, which records that Windows keeps a file handle open after the process is killed — knowledge that is invisible in the code and expensive to rediscover.

What must never go in

A repository keeps everything forever, and that cuts both ways. Deleting a file in a later snapshot does not remove it from the history; anyone who clones the project still gets every version of it. So the decision about what to record has to be made before the first commit, not after.

This project excludes three categories, listed in a file called .gitignore:

ExcludedWhy
portfolio.db Real positions, share counts, and cost basis. Personal financial data.
build/, node_modules/, .venv/ About 1.3 GB, and every byte of it regenerable from what is tracked.
.env Machine-specific settings. .env.example documents the options instead.
This one is not hypothetical

portfolio.db holds someone's actual holdings. Committing it once to a public repository publishes their finances permanently — and because history is preserved, removing it afterwards does not undo that. The only reliable fix is rewriting history and treating the data as compromised.

Write the .gitignore first, then run git status and read the list before your first commit. It takes ten seconds and it is the only moment when this is cheap.

How .gitignore actually works

It is a plain text file at the top of the project, one pattern per line, # for comments. The pattern rules are worth knowing properly, because "I thought that was ignored" is a common way to publish something you did not mean to.

PatternMatches
portfolio.dbThat name, in any directory
/portfolio.dbOnly at the project root
build/Directories called build, and everything inside
*.dbAny file with that extension
docs/**/*.pngPNGs at any depth under docs
!keep-this.dbAn exception — un-ignores something an earlier pattern caught
The rule that catches everybody

.gitignore only affects files git is not already tracking. If you committed a file and then added it to .gitignore, nothing happens — git keeps tracking it, because you already told it to.

You have to untrack it explicitly. This removes it from the repository while leaving your copy on disk: 

git rm --cached portfolio.db

And note what that does not do: the file stays in every commit that already contains it. Untracking stops the bleeding; it does not clean the wound. See below.

Two commands make ignoring behave predictably instead of mysteriously: 

git status --ignored           # what am I skipping?
git check-ignore -v secrets.txt # WHICH rule is skipping this file?

The second one prints the file and line number of the pattern that matched, which turns "why isn't this showing up" from a guessing game into a lookup.

Secrets are the category that actually bites

Personal data like this project's database is easy to reason about, because you know it is sensitive. Credentials are harder, because they arrive innocently: a config file with the real value in it "just to test", an API key pasted into a script, a .env that gets committed the one time you run git add -A before writing the ignore rule.

The reassuring story people tell afterwards is some version of "it was expired anyway, and nobody reads my repository". Both halves are luck rather than safety, and the second one is simply not true:

  • Public activity is a firehose, and it is monitored. GitHub publishes a stream of public events. Automated scanners watch it and fetch new commits within seconds. There are well-documented cases of cloud keys being used for crypto-mining minutes after being pushed. Nobody has to be interested in your project for this to happen — they are interested in the pattern AKIA….
  • A repository is cloned, forked, and cached. Once fetched, it is on somebody else's disk, and no amount of deleting on your side reaches it.

GitHub does help. Secret scanning recognises the formats of many providers' tokens and notifies the provider, which will often revoke the key on your behalf. Push protection goes further and blocks the push before it lands. Both are on by default for public repositories, and neither covers everything — a database of positions or a homegrown token has no recognisable shape.

If you do commit a secret, the order matters

Most people get this backwards. They spend an hour rewriting history while the credential is still live and still working.

  1. Rotate it first. Revoke the token, regenerate the key, change the password. This is the only step that actually stops the bleeding, and it works no matter who already has a copy. Do it before you touch git at all.
  2. Assume it was used. Check logs, billing, and access history for the account it belonged to.
  3. Then clean the history. git filter-repo is the current tool for this (filter-branch is deprecated and slow). Cleaning rewrites every affected commit, which changes their identifiers.
  4. Force-push, and warn anyone else. Rewritten history breaks every existing clone; collaborators have to re-clone or reset. This is why the cleanup is the painful step and rotation is the effective one.
  5. Ask GitHub Support to purge caches. Forks and pull request views can retain the old objects even after you rewrite.
  6. Stop it recurring. Keep real values in a .env that is ignored, commit a .env.example with the keys and fake values, and consider a pre-commit scanner such as gitleaks.
The honest summary

A leaked credential is not recoverable by deletion — only by replacement. Treat the git cleanup as tidying up after the incident, not as the fix for it.

What a commit should contain

One idea. The import feature and the guide rewrite are two commits, not one, because they are two things a future reader might want to understand or undo separately. A commit spanning four unrelated changes cannot be reverted without taking the other three with it.

This is also why the project's first commit is unusually apologetic: it contains the entire application, because there was no history to preserve. Every commit after it is a single change with a reason attached. Starting on day one costs one command; starting at v1.1.0 means the first snapshot is just "everything, somehow".

Getting it to other people

A public repository serves two audiences who want completely different things from it. Most confusion about "publishing an app" is really confusion about which audience you are talking to.

Someone arriving at your project is either a developer, who wants the source so they can read, change, or build it, or a user, who wants the finished program and does not care that it is written in Python. Serving one well and the other badly is the usual failure.

Getting the tools onto your machine

Git on its own can push code. The GitHub CLI (gh) adds the GitHub-specific things git knows nothing about, because they are not part of git: creating repositories, opening pull requests, and publishing releases with files attached.

You install a command-line tool, type its name, and the terminal insists it does not exist. Nothing is broken. A shell reads the PATH when it starts, so a terminal you had already open predates the installation and will never see it.

Open a new terminal. This happened twice while building this project — once for Node, once for gh — and it is far and away the most common "the install failed" that is not an install failure.

Tags: naming the commit a release was built from

A tag is a permanent label on one snapshot. Versions move forwards; a tag stays put. When a user reports a bug in 1.2.0, the tag is what lets you look at exactly the code they are running, months later, after everything has moved on. 

git tag -a v1.4.0 -m "Tests, refactoring, and the docs for both"
git push origin v1.4.0

The convention is a v prefix on the version number, and the tag should point at the commit you actually built the installer from — not one made afterwards.

What a GitHub Release actually is

Three things stapled together: a tag, some notes written for humans, and one or more attached files. The attachments are stored separately from the repository, which is exactly why binaries belong there.

The whole publishing sequence, end to end:

  1. Commit the change

    With a message explaining why it exists.

  2. Bump the version and rebuild

    Re-freeze the backend if any Python changed, then rebuild the installer.

  3. Test the packaged build

    Not the dev one — see Part 08.

  4. Tag and push

    git push origin main

  5. Create the Release and attach the installer

    On the web, or in one command if you have the GitHub CLI:

  "build/desktop-dist/Horizon Holdings Setup 1.4.0.exe" \
  --title "v1.4.0" --notes-file CHANGELOG.md
Tell users what they will see

An unsigned installer is not a neutral experience. Windows shows a SmartScreen warning users must click past, and if Smart App Control is enforced it refuses to run the app at all. macOS refuses outright without a paid certificate.

None of that is a defect, but a user who is not warned assumes your app is malware. Say it plainly in the README, and say what to do about it.

The README is the front door

It is the first and often only thing anyone reads. It has to serve both audiences within the first screen: a link to the Releases page for users, and build instructions for developers. If a visitor cannot tell within fifteen seconds which of those they are, the README has failed.

Licensing: what other people may actually do with it

Publishing source code does not give anyone permission to use it. This surprises people. With no licence file, ordinary copyright applies and the default is all rights reserved: visitors may read the code, and may not legally copy, modify, or build on it. A public repository with no LICENSE is a common and almost always unintended way of saying no.

Licences come in three broad families.

Permissive MIT, Apache 2.0, BSD Use it in anything at all, including closed commercial products Credit. Apache adds an explicit patent grant
Copyleft GPL 3.0, AGPL 3.0 Use it — but distributing a modified version obliges them to publish their source too Derivatives stay open
Public domain CC0, Unlicense Anything, without even crediting you Nothing, by design

Choosing between them is one question, and it is not a technical one: if a company took this, improved it, and sold it without telling you — is that fine, or should they have to share the improvements back? "Fine" means permissive. "Share back" means copyleft. Everything else is detail.

This project is MIT: the shortest permissive licence, the one Chart.js and Electron themselves use, and the one that puts the fewest obstacles between a student and reusing something they read here. Copyleft would have been a defensible choice for different goals.

Your licence does not cover what you bundled

This repository ships Chart.js and three font families inside it, and the installer additionally contains Python, Electron, and their whole dependency trees. Choosing MIT says nothing about any of them. Each keeps its own licence, and some place obligations on whoever redistributes them.

The fonts here are under the SIL Open Font Licence, which requires the licence text to travel with the fonts and forbids selling them on their own. Meeting that took one file — THIRD-PARTY-NOTICES.md — which was written only because this section was. Nearly every application carries obligations like these, and a surprising number quietly fail to meet them.

Mechanically it is one file called LICENSE at the root, with no extension. GitHub detects it, shows the licence name on the repository page, and makes the project findable by licence. Add your name and the year; that is the whole ceremony.

Part 13

Building with an AI assistant

This application was built with one. That is worth being specific about, because the useful lessons are not the ones in the marketing.

Most of the code here was written by an AI assistant working from instructions, running commands, reading the output, and fixing what it found. The interesting question is not whether that works — it plainly does — but where it works and where it does not.

The obvious follow-up — then how does anyone know it does what it claims? — has an answer that has nothing to do with AI, and it is Part 09. You find out the same way you find out about code you wrote yourself and have since forgotten: by writing down what it is supposed to do, separately, and checking. "Who wrote it" changes how suspicious you feel. It does not change the method.

Where it genuinely helped

  • Problems with known shapes. Supervising a child process, picking a free port, polling for readiness, a PyInstaller spec, a .gitignore. These are solved problems with well-known traps, and recalling all of them at once is exactly the shape of task this is good at.
  • Actually running things. The single most valuable thing it did was run the packaged build and read the result. Two real bugs surfaced that way — neither was found by reading code, including by the model that wrote the code.
  • The tedious-but-important. This document, the code comments explaining why, the commit messages. Work that is genuinely valuable, genuinely boring, and therefore usually skipped.

Where it failed, in this project

Three bugs reached a built artifact. All three were written by the assistant, and it is worth looking at what they have in common.

BugWhy it slipped through
Migration silently doing nothing once packaged The code was correct in the environment it was tested in. The failure only exists in a different one.
Dismissing a dialog choosing the destructive option Every line was individually reasonable. The bug was in the interaction between a default and human behaviour.
A CSS comment left unclosed by an edit A careless edit to surrounding text, hidden by the browser's error recovery.

The pattern: AI-written code fails in the same places human-written code fails — at boundaries between environments, at defaults, and in the gap between "looks right" and "was run". What it does not do is fail obviously. The code reads well, the comments are confident, and the reasoning is plausible. None of that is evidence it works.

The habit that actually helps

Ask for verification, not just code. "Write the import feature" produces something plausible. "Write it, then run the packaged build with an empty data directory and show me what happened" produces something tested. The second is barely more effort and a different category of result.

What stayed human

Every decision that shaped the project came from the person, not the assistant: that it should be an Electron app at all, that the Python backend should be frozen rather than rewritten in JavaScript, that closing the window should keep the scheduler running, that the tray needed to say which of two pipelines it was fetching. The assistant had opinions and argued for some of them. It did not get to choose.

This matters more than it sounds. Those decisions encode what the thing is for — a NAV series that must stay unbroken for decades, on one person's laptop, without a subscription. An assistant can weigh a tradeoff once you state the goal. It cannot tell you what the goal should be.

Why this makes Part 11 more important, not less

Working this way, changes arrive faster and in larger pieces than when typing every line yourself. Four files can change in a minute. That is precisely the situation in which "what changed since it last worked?" becomes both harder to answer from memory and more valuable to answer.

The version control this project spent nine parts not having is not optional overhead when an assistant is involved. It is the mechanism by which you stay the one in charge of a codebase that is growing faster than you can read it.

Part 14

What transfers

The parts of this that are not about portfolios, Python, or Electron.

Write the raw data down before you compute anything

Fetching and calculating are separate steps, and the fetch is the one you cannot repeat — yesterday's prices are gone tomorrow. Persist first. Then a bug in the calculation costs you a re-run, not the data.

Refuse to produce a wrong answer

When an input is missing, the instinct is to substitute something and carry on — zero, the last value, an average. For anything that becomes a permanent record, refusing is better. A gap announces itself; a plausible wrong number never does.

Anything time-dependent needs a way to lie about time

Code that behaves differently on the first of the year is untestable unless you can fake the date. Build that in from the start; retrofitting it is painful.

Test the thing you ship, not the thing you build

A development build and a packaged one differ in ways that are invisible until they aren't: where files resolve, what is read-only, what state already exists. Every bug in this project that reached the "shipped" stage was of that kind, and each was found in the first five minutes of running the packaged artifact.

Isolate the parts that vary

One file talks to the internet. One process knows about the operating system. The interface knows nothing except a list of URLs. Each of those boundaries is why some later change turned out to be cheap — the desktop version cost a few small edits to Python precisely because nothing in the logic assumed how it was being run.

Leave the reasoning behind, not just the code

The comments in this project explain why, and often name the specific bug that motivated a choice — the 2.17% phantom loss, the daily false alarm in the logs, the backup that silently dropped recent transactions. Code says what it does. Only a comment can say what happens if you undo it.

The version of this that matters most

Six months from now the person most confused by your code is you. Every "obvious" decision you did not write down will have to be rediscovered — and the cheapest moment to record it is the moment you make it.
